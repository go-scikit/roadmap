# Performance campaign

Goal: show, for every public function of the go-scikit stack, that it is at least as fast as its
reference (NumPy, SciPy, statsmodels, mpmath, or the C library it ports) **on one core**, and
close every gap that the measurement finds — the algorithm first, then a SIMD kernel from
[go-simd](https://github.com/go-simd) generated by [go-asmgen](https://github.com/go-asmgen/asmgen).
This page is the design: what exists, the shared tool, the kernels, the order. No optimisation is
done here.

Written 2026-11-07. Everything below cites a file that was opened, at the commit given in
[Sources](#sources).

## 1. Rules

1. **One core on both sides.** Go under `GOMAXPROCS=1`, set outside the timed interval; the
   reference with `OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `MKL_NUM_THREADS` and
   `VECLIB_MAXIMUM_THREADS` at 1 (the set go-simd/floats `bench/numpycmp` already uses). An
   all-cores column may be shown, never used as the verdict.
2. **The same data on both sides**, generated by the same formula (go-statistics/stats and
   go-numerics/special use `lo + (hi-lo)·frac(0.618…·i)`), and checked by hashing the arguments
   the reference receives (stats does it with `-perf.datahash`).
3. **The same statistic on both sides.** Each sample is a loop calibrated to the same minimum
   duration, timed inside its own process (the pipe is not counted, as go-bignum/bigfloat's
   `oracle/mpmath.go` already does); a round is one sample per side; the verdict is on the
   median over rounds, with the quartiles kept. Today the harnesses differ: signal reports the
   best of 5, stats the median of 7, special the median of 5, and floats' `numpycmp` compares
   Go's mean ns/op with `timeit`'s best of 5 — two different statistics in one ratio.
4. **Interleaved rounds**, alternating the order (Go then reference, then reference then Go), so
   that a change in the host's load hits both sides alike.
5. **Load gate.** The 1-minute load is read before every round and stored with it. At or above
   8 the tool waits (or refuses, by flag); a run whose rounds were not all under the gate gives
   no verdict. Allocation counts are exact under any load and are checked everywhere; times are
   not. (While this page was written the load went from 6.6 to 136: a timing campaign on this
   machine is a matter of waiting for a window, and the tool must do the waiting.)
6. **Verdict.** `ratio = Go / reference` (median). *Slower* when the Go first quartile is above
   the reference third quartile; *tie* when the quartile ranges overlap; *faster* otherwise. A
   slower row is an open defect, filed (section 5).
7. **Bit parity is a property of a kernel, not of a speed-up.** A kernel claimed bit-identical to
   NumPy or SciPy runs without FMA and in the reference's order (floats' `SumPairwise` keeps
   NumPy's eight accumulators as lanes; its `*NoFMA` kernels round every product and sum as NumPy's
   temporaries do). A fused or reordered kernel is allowed only where the result is validated by
   a tolerance, and its table row says so.

## 2. Inventory

### 2.1 Count

[`tools/perfinventory`](../tools/perfinventory/main.go) counts, per repository, the exported
functions and exported methods of exported types in the public packages (no `internal`, `cmd`,
`tools`, `bench`, `benchmarks`, `examples`, `testdata` element, no `main`; `Error`, `String`,
`Format`, the `Marshal` family, `Unwrap` and `Is` left out). Every module of the repository is
loaded with its tests through `golang.org/x/tools/go/packages`, so each use is resolved by the
type checker. A function is

- **ref** when it is used in timing code (a benchmark, a function calling `time.Now` or
  `time.Since`, a `perf*` file that times, a harness package that times) whose code — string
  literals, identifiers, `import "C"`, not comments — names a reference;
- **noted** when it is timed and the reference is named only in comments: the comparison is run
  by a script outside Go (`run.sh`, `bench_numpy.py`, …);
- **bench** when it is timed and no reference is named;
- **none** otherwise.

Denominator: **2081** public functions. **234 (11 %)** are timed by Go code that drives the
reference, 131 more are timed by a Go benchmark that an outside script pairs with the reference,
53 are timed with no reference, and **1663 (80 %) are not timed at all.** go-statistics/models has

What the count is not:

- **A lower bound where a harness reaches functions indirectly.** stats' `docs/perf.md` says its
  harness times 355 cases covering every public operation; the tool sees 112 functions referenced
  directly, because the cases reach most distribution methods through tables and interfaces,
  which the direct-reference rule does not credit. The shared tool removes the ambiguity: its
  case registry names the function each case measures (section 3).
- **Not a statement that the comparison is right.** A *ref* row says the code drives a reference,
  not that it does so on one core or with the same statistic (see 2.2).

## 3. The shared tool: `refbench`

### 3.1 Home

**Proposed: a new public repository `go-scikit/refbench`, created with `ghnew -public`.** It is a
library first: every repository registers its cases in Go, in a `perf_test.go`, as stats,
special and signal already do, so the code has to be importable from test files, small, and
free of cgo. go-fleettools is a collection of operations commands; making every numerical
library's test build depend on it is the wrong direction. What already exists is reused, not
rewritten:

- the load reader and waiter: `github.com/go-fleettools/fleettools/loadavg` (`Avg1`, `Wait`,
  darwin and Linux), imported; if its module weight matters, it moves to its own module rather
  than being copied;
- the alternation and the fail-stop rule of `go-fleettools cmd/abbench` (a child that fails stops
  the run: a series with a hole is biased, not smaller), and `cmd/hostload`'s `/proc/stat` busy
  check on Linux hosts;
- stats' JSON-lines Python worker (`perf_scipy_test.go`: one `uv` process, one request per line,
  arguments cached per `(setup, n)`, a `hash` request to check the data);
- signal's report format, and floats' `numpycmp` table.

### 3.2 Design

- **Case registry** (Go): name, the public function it measures (a function value, so the name is
  resolved by the compiler and the inventory can match it), sizes, input formula, Go body,
  reference call, parity class (`exact` / `tolerance` / `none`) and the expected allocations
  per call.
- **Python references** through one long-lived worker started as
  `uv run --no-project --python 3.12.12 --with-requirements refs.txt python -I -c <worker>`,
  where `refs.txt` is committed in the repository with exact versions and hashes (NumPy, SciPy,
  statsmodels, mpmath; the versions in [COVERAGE.md](../COVERAGE.md) — numpy 2.5.3 there,
  2.5.4 in floats and stats: one version is chosen and pinned everywhere). The worker reports
  `numpy.__version__`, `scipy.__version__` and the BLAS in use; they go in the table header.
- **C references** through a subprocess speaking the same JSON-lines protocol, built by the
  tool from committed sources with the flags the reference requires (predicates.c: no FMA
  contraction), so the library never needs cgo. A repository that already has a cgo module
  (predicates `bench/`) may keep it, timed through the same runner.
- **Runner**: calibrated loops on both sides, rounds interleaved and alternated, the load read
  and recorded before every round, `--on-load=wait|refuse`, `--max-load 8` by default.
- **Outputs**: `docs/perf-table.md` (generated: date, commit, Go version, reference versions,
  machine, load min/median/max, one row per case with both medians, the ratio, the verdict, the
  parity class) and `docs/perf.json` (the same plus every round's samples and load, schema
  versioned). `docs/perf.md` stays the hand-written method and analysis page — eleven of the
  repositories already have one, and stats and special already generate a `perf-table.md` beside
  it, so the names follow the existing convention rather than a new `performance.md`.
- **CI mode** (`go test -run TestPerf -perf.ci`), on every pull request, no Python, no timing:
  1. each case runs once and its allocations per call must equal `docs/perf.json`'s (a change
     either way fails: an increase is a regression, a decrease must be recorded);
  2. `docs/perf-table.md` must be what `docs/perf.json` generates (no hand edits);
  3. every public function (the inventory's rule, section 2.1) is registered or listed in
     `docs/perf-exempt.md` with a reason — the denominator is a gate, not a note.
- **Timing mode** runs only on the quiet machine (this darwin/arm64 host, load < 8) and, as
  indicative, on a scheduled amd64 runner whose rows are labelled as such (floats' README
  already reports CI EPYC numbers this way). Timing never runs in a pull request's checks.

## 4. go-simd and go-asmgen

### 4.1 What there is

- **go-simd/floats** (v0.7.0 is what optimize, sparse, poly and signal require): `Dot`, `Sum`,
  `Min`, `Max`, `Distance`, `CosineSimilarity` (float64 and float32); fused `Axpy`, `Xpby`,
  `AxpyDot`, `Scale`, `Mul`, `Axpby3`, `Clamp`, `MaxAbs`; NumPy-exact `AxpyNoFMA`, `XpbyNoFMA`,
  `Axpby3NoFMA`, `AxpyDiffNoFMA` and `SumPairwise`. Kernels generated by go-asmgen for amd64
  (AVX2+FMA) and arm64 (NEON); the other four architectures run portable loops until a kernel is
  measured faster on real silicon.
- **go-asmgen**: ABI0 builders for six architectures, SIMD through `Raw`, CPU feature probes,
  the instructions `cmd/asm` lacks as checked `WORD`s (arm64 multiply-by-element, ppc64le VSX
  float64/float32 arithmetic, s390x float32 vector ops, loong64 vector FMA), and go-fft's kernel
  builders (`fft/amd64`, `fft/arm64`, `fft/riscv64`, `fft/s390x`, including the complex products).
  Its README lists typed vector loads and vector types as the main remaining items.
- **go-simd/highway** (a fork of go-highway): not used by the stack; needs `GOEXPERIMENT=simd`
  on amd64 and documents about 4 ULP for its math, so it fits neither the stable-Go rule nor
  bit parity. Not adopted.
- **go-simd/histogram**: a byte-value histogram; nothing in the stack's `histogram` (float
  binning) maps to it.

### 4.2 Which hot loops use what today

From the call sites of `floats.` in the stack's sources:

| kernel | used by |
|---|---|
| `Mul`, `MaxAbs`, `Clamp`, `Axpby3` | optimize QP (ADMM step, scaling, polishing, checks) |
| `Dot`, `Axpy`, `Scale`, `Xpby` | optimize trust-constr and its dense linear algebra; sparse `iter` (CG); poly QR; signal (`linalg`, `resample`, `spectral`) |
| `AxpyDot` | sparse `iter` (CG residual update) |
| `AxpyDiffNoFMA`, `SumPairwise` | optimize differential evolution (bit-identical to SciPy) |
| `Sum` | signal (`spectral.go`: the segment mean) |

`floats.Sum` adds in lane order, not NumPy's pairwise order; where signal's spectral results are
compared with SciPy by equality, that mean should be `SumPairwise` — to check in W1.

go-ndarray does not import go-simd/floats. It has its own go-asmgen kernels in
`internal/kernels`: `Add`, `Sub`, `Mul`, `Div`, `Sqrt`, `Sum` (NumPy's pairwise order), `Max`,
`Min`, `Clip`, `Dot1D`, `Exp`, `Log`, float32 `Bin32`, `Max32`, `Min32`, `AddBlocks8F32`,
`Exp32`, `Log32`, axis reductions and GEMM (float64 and float32). Several of these do what a
floats kernel does (`Mul`, pairwise `Sum`, `Max`/`Min`, `Dot1D`, `Clip`/`Clamp`): two
implementations of one operation, against the rule that a kernel lives once, in the lowest
library that every user can import. go-simd/floats has no dependency, so it is that library.

### 4.3 Kernels to add or move

Each in one place; *parity* says how it is validated.

| # | kernel | lowest home | serves | parity |
|---|---|---|---|---|
| K1 | Move ndarray's 1-D kernels down: `Add`, `Sub`, `Div`, `Sqrt`, `Max`/`Min` with NumPy's NaN rule, float32 `Bin32`, extrema and pairwise sum (`AddBlocks8F32`), `Exp`/`Log` float64 and `Exp32`/`Log32`; ndarray then calls floats and deletes its copies of `Mul`, `Sum`, `Dot1D`, `Clip` | go-simd/floats | ndarray ufuncs and reductions, and through it stats, special `nd`, optimize | exact for the arithmetic, `Sqrt`, extrema and pairwise sums; `Exp`/`Log`: ULP-bounded (ndarray's tests), labelled tolerance against NumPy |
| K2 | Elementwise polynomial evaluation over an array of points: Horner, and Clenshaw for Chebyshev/Legendre series, unfused | go-simd/floats | poly (`polyval`, `chebval`, `legval`, …); special's rational approximations in its array path; stats pdf/cdf through special | exact: the lanes run over different points, so each point sees NumPy's order; for special, exact against its own scalar code |
| K3 | Gathered dot product `Σ val[k]·x[idx[k]]` (a CSR row) | go-simd/floats | sparse CSR mat-vec, sparse `iter`, optimize QP on sparse KKT systems | tolerance (lanes reorder SciPy's sequential sum); the sequential unfused loop stays as the exact path |
| K4 | Complex elementwise products (`CMul`, conjugate product, `|z|²`) over `[]complex128` | go-simd/floats, emitted by go-asmgen's existing `fft/*` complex-product builders under floats' symbols (go-fft keeps its internal kernels until it switches) | signal (`fftconvolve`, `hilbert`, frequency responses), ndarray complex ufuncs, special `cmplx` arrays | exact against the Go scalar formula; against NumPy to be established by its oracle, since a C compiler may contract the products |
| K5 | `SearchSorted` over many points, and the linear-interpolation step of `np.interp` in NumPy's operation order | go-simd/floats | interp (`interp1d`, `np.interp`), ndarray `searchsorted`, stats empirical CDFs | exact (indices are integers; the step is unfused, in NumPy's order) |
| K6 | Multi-term linear combination `dst = y + h·Σ aⱼ·kⱼ` (Runge–Kutta stages) | go-simd/floats | integrate (`solve_ivp` RK23, RK45, DOP853) | tolerance (SciPy forms it with a matrix product, whose order BLAS chooses); fused allowed, labelled |
| K7 | Vector `cos`/`sin` | go-simd/floats, beside K1's `Exp`/`Log` | signal windows and spectral code, ndarray ufuncs | tolerance (ULP-bounded) |
| K8 | Batched floating-point filter for `orient2d`/`incircle`/`orient3d`/`insphere` over arrays of point records, falling back to the exact stages per lane | go-geometry/predicates (its only user) | predicates, later Delaunay (COVERAGE.md item 7) | exact: the filter is conservative, the sign is the exact predicate's |

Not kernels, but the same rule:

- **Double-double arithmetic exists twice**: `go-numerics/special/dd` and
  `go-statistics/stats/internal/dd` have the same package comment and the same `zz_exptable.go`
  and `zz_logtable.go`. stats already depends on special, so stats imports `special/dd` and
  deletes its copy.
- **Scatter-add** (the `y[idx[k]] -= a·val[k]` of sparse LDL, where QDLDL's refactor leads by 11–21 %) has no
  vector form on AVX2 or NEON, which have gathers and no scatter (go-simd/histogram's README
  works through the same limit). The QDLDL gap is algorithmic first.
- **special's 0.07×–0.70× rows** are scalar against scalar: SciPy's ufunc loops are one-thread C
  calling scalar code too. They are profiled before any kernel is written (the cost of
  `math.Exp`/`math.Log` against the C library's, bounds checks, coefficient loops); K1 and K2 are
  what follows if the profile points at elementary functions or polynomial evaluation.
- **GEMM stays in go-ndarray**: every user of dense matrix products already imports it.

## 5. Order of the campaign

### Waves

| wave | content | where it runs |
|---|---|---|
| W0 | Create `go-scikit/refbench` (library, runner, Python and C workers, table and JSON writers, CI mode, the inventory rule as a gate); pin `refs.txt`; this page and `tools/perfinventory` | CI for the tool's own tests |
| W1 | Migrate the three harnesses closest to the rules, to prove the tool on known numbers: go-dsp/signal, go-simd/floats (`numpycmp` retired), go-geometry/predicates (C worker; issue #4) | quiet machine for the tables; CI mode from the first PR |
| W2 | The two largest gaps: go-numerics/special first (stats inherits 51 slower rows from it), then go-statistics/stats (236 slower rows) | quiet machine |
| W3 | go-ndarray (re-measured on one core against the pinned NumPy; draws measured for the first time), go-fft (its `run.sh`/`report.py` folded into the tool; FFTW through the C worker), go-sparse (QDLDL through the C worker; issue #10) | quiet machine |
| W4 | go-numerics/optimize and integrate (their shell drivers folded in), go-approx/interp and poly, go-bignum/bigfloat (mpmath worker), go-statistics/models when its first code lands | quiet machine |
| K | Kernel work (section 4.3) starts from the issues the waves file, in the order the tables rank them by total time lost; every kernel PR re-runs the affected repositories' tables | quiet machine; CI checks parity and allocations |

Each wave registers every public function of its repositories (or exempts it with a reason),
so that by its end the repository's row in section 2.1 is all *ref* and *exempt*; then it
measures; then it files.

### A slower row becomes an issue

`refbench issues` (a command of the same repository) reads `docs/perf.json` from a valid run:

- for each *slower* row it opens or updates one issue per case in that repository, titled
  `perf: <case> is <ratio>x slower than <reference> on one core`, labelled `perf`, with the row,
  the machine, the load of every round, the reference versions and the commit;
- for each row that is no longer slower in a valid run it comments the new row and closes the
  issue;
- a run that fails the load gate files nothing.

go-fleettools has a `ghissue` command; it is read before this one is written, and reused if it
does the job.
